## 1. Telephony stack: ModemManager vs oFono, and the cheapest integration point for a Samsung-IPC daemon

### Takeaway
ModemManager's D-Bus API is the de-facto contract: every desktop client relevant here (GNOME Calls,
Chatty, Spacebar, mmsd-tng, NetworkManager, systemd-networkd ≥ 260, WirePlumber's call-profile module)
speaks it, while oFono reaches most of them only through the ofono2mm shim. A native ModemManager plugin
is the "upstream-clean" route but the most expensive. For a single device the cheapest route is a single
Samsung-IPC daemon that also exposes the ModemManager D-Bus API itself, the way ofono2mm already
replaces ModemManager on Droidian. A virtual-AT bridge (samsungipcd) is the quickest prototype, but it
forces PPP data and leaves feature gaps.

**Samsung IPC protocol vs this board**
- [GEN][C] libsamsung-ipc's FMT header is `struct ipc_fmt_header { u16 length; u8 mseq; u8 aseq; u8 group; u8 index; u8 type; }`. Groups: PWR 0x01, CALL 0x02, SMS 0x04, SEC 0x05, PB 0x06, DISP 0x07, NET 0x08, SND 0x09, MISC 0x0A, SVC 0x0B, SS 0x0C, GPRS 0x0D, SAT 0x0E, CFG 0x0F, IMEI 0x10, GPS 0x11, SAP 0x12, RFS 0x42, GEN 0x80. Request types EXEC/GET/SET/CFRM/EVENT 0x01-0x05; response types INDI/RESP/NOTI 0x01-0x03 — [include/protocol.h](https://git.replicant.us/replicant/hardware_replicant_libsamsung-ipc/plain/include/protocol.h)
- [HW][C] The downstream kernel's FMT header is `sipc_fmt_hdr {u16 len; u8 msg_seq, ack_seq, main_cmd, sub_cmd, cmd_type}` (7 B), and libsec-ril.so logs "MainCmd=%d SubCmd=%d CmdType=%d" — `research/modem/SS333_LLI_BRINGUP.md` §2.3 and §5.3. It has the same layout as libsamsung-ipc's header.
- [HW][C] libsamsung-ipc supports **herolte** (Galaxy S7, `TARGET_SOC := exynos8890`), whose LineageOS board config sets **`BOARD_MODEM_TYPE := ss333`**, the same modem type as SM-T715 (`src/device_gts28ltexx/BoardConfig.mk:13`) — [universal8890-common BoardConfigCommon.mk:115-131](https://github.com/LineageOS/android_device_samsung_universal8890-common/blob/lineage-18.1/BoardConfigCommon.mk), [libsamsung-ipc devices/](https://git.replicant.us/replicant/hardware_replicant_libsamsung-ipc/tree/samsung-ipc/devices)
- [HW-adjacent][C] herolte support (copyright 2020; commits dated 2021-02-22…2021-03-03) boots the CP through `/dev/umts_boot0` with `IOCTL_MODEM_RESET`, `IOCTL_SECURITY_REQ`, `IOCTL_DPRAM_SEND_BOOT` (BOOT/MAIN/NV chunks from the RADIO TOC) and `IOCTL_MODEM_DL_START`, then a 0x900d/0xa00d and 0x9f00/0xaf00 handshake. It looks for `"/dev/disk/by-partlabel/RADIO"` ("PostmarketOS"). It reuses the XMM626 FMT/RFS send/recv code, and **`herolte_gprs_activate/deactivate` are TODO stubs that return 0** — [herolte.c](https://git.replicant.us/replicant/hardware_replicant_libsamsung-ipc/plain/samsung-ipc/devices/herolte/herolte.c)

### Inferences
- [HW][L] Because the SS333 FMT framing matches libsamsung-ipc byte for byte, and libsamsung-ipc already drives an `ss333`-type CP (herolte), most of the CALL/SMS/SEC/NET/SS/SND message codecs can probably be reused or ported. What will differ: the boot path (SM-T715 uses LLI `DL_START`+`FW_UPDATE`+`write()`, not `DPRAM_SEND_BOOT`, per `SS333_LLI_BRINGUP.md` §3.4) and possibly newer message variants (IPv6 PDP, VoLTE). libsamsung-ipc is GPL-2.0+, which constrains the daemon's license if code is linked or copied.
- [GEN][L] Integration options, ranked by cost for this single device:
  1. **The IPC daemon exposes the MM D-Bus API itself** ("MM impersonation", the ofono2mm pattern without oFono). It is one process that owns `umts_boot0` (cbd replacement), `umts_rfs0` (NV/RFS server), `umts_ipc0` (FMT) and `rmnet*`. It must implement Manager + ObjectManager, Modem, Modem3gpp, Ussd, Simple, Sim, Voice, Call, Messaging, Sms and Bearer. Data stays on the raw-IP rmnet netdev. NM, Calls, Chatty, mmsd-tng, networkd and WirePlumber all work unchanged. ofono2mm (~2.4 k lines of Python) shows the size of that API layer. Lowest cost; no kernel or MM changes.
  2. **oFono driver + ofono2mm**: a C atom driver set (netreg, voicecall, sms, sim, ussd, gprs/gprs-context, radio-settings) in the oFono tree, which has no Samsung-IPC driver upstream (Arch does not package oFono). It needs a three-layer stack (IPC → oFono → Python shim → clients). Only worth it if oFono's SIM toolkit or `isimodem`-style driver structure is wanted.
  3. **Native MM plugin** (precedent: XMM7360 RPC, §6). It needs a port MM can discover (`/dev/umts_ipc0` is a `misc` device, not tty/net/usbmisc/wwan). That means either a kernel change that registers a wwan port (no `WWAN_PORT_*` type exists for Samsung IPC; adding one is a kernel UAPI change, as XMMRPC was) or MM core changes. It also needs in-tree MM development and a long upstream review.
  4. **Virtual AT bridge** (samsungipcd): quick to stand up and no MM changes. But the tty must be visible to udev (legacy BSD ptys or CUSE), data goes over PPP emulation in userspace instead of the rmnet netdev, and many features are missing.
- [GEN][S] A hybrid is plausible: prototype with samsungipcd plus generic MM to validate the IPC layer, then move to option 1 for production.

### Gaps
- Whether the SS333 firmware on SM-T715 uses the exact message set libsamsung-ipc implements (e.g. `IPC_GPRS_IP_CONFIGURATION` has IPv4-only fields in libsamsung-ipc): unverified without traffic captures.
- Whether herolte telephony (calls/SMS/data) actually works with libsamsung-ipc on postmarketOS: no source found. The squeak-phone and pmOS pages were unreachable (Anubis/redirect). UBports reports calls and SMS working on herolte, but through the Android RIL, which is not comparable.
- No first-hand statement found from MM maintainers about accepting a Samsung-IPC plugin.

## 2. Mobile data on a raw-IP netdev (NetworkManager, ModemManager, systemd-networkd) and what the daemon must do for a PDP context

### Takeaway
NetworkManager and systemd-networkd only need, from MM (or an MM-API implementation), the bearer's
`Interface` name plus `Ip4Config`/`Ip6Config` (method STATIC, DHCP or PPP; address; prefix; gateway;
DNS; MTU). They then configure the netdev themselves, including IPv6 SLAAC. The downstream rmnet
netdevs are `ARPHRD_PPP`. Mainline IPv6 autoconf ignores that type, so the port should use
`ARPHRD_RAWIP` (or `ARPHRD_NONE`) like every mainline WWAN driver does.

### Cited Findings
- [HW][C] Downstream `vnet_setup` creates rmnet with `ndev->type = ARPHRD_PPP`, `IFF_POINTOPOINT | IFF_NOARP | IFF_MULTICAST`, `addr_len = 0`, `hard_header_len = 0`, `mtu = ETH_DATA_LEN`. It is used whenever `use_handover == 0` (this board) — `src/kernel_universal5433/drivers/misc/modem_v1/modem_io_device.c:1671-1681, 1800-1807`. RX sets `skb->protocol` from the IP version nibble — same file `:309-315`.
- [HW][C] rmnet0-3 ↔ SIPC channels 10-13 (PDP_0..3), `ATTR_NO_LINK_HEADER` (bare IP). `multipdp` (MULTI_RAW, ch 0) is rild's control node — `SS333_LLI_BRINGUP.md` §5.4. libsec-ril reads a property `net.temp.mtu` — §5.3.
- [GEN][C] Mainline `addrconf_dev_config` only auto-configures IPv6 on ETHER, FDDI, ARCNET, INFINIBAND, IEEE1394, TUNNEL6, 6LOWPAN, TUNNEL, **NONE** and **RAWIP**; for `ARPHRD_NONE` it forces `addr_gen_mode` from EUI64 to RANDOM. **`ARPHRD_PPP` is not in the list** — `src/linux-6.12/net/ipv6/addrconf.c:3500-3531`. RAWIP takes its EUI-64 from `perm_addr` (`:2377-2385, 2408-2409`).
- [GEN][C] Mainline WWAN netdevs use `ARPHRD_RAWIP` (`mhi_wwan_mbim.c:599`, `qcom_bam_dmux.c:418`, `rmnet_vnd.c:282`, `ipa_modem.c:227`) or `ARPHRD_NONE` (`iosm_ipc_wwan.c:152`, `t7xx_netdev.c:251`, `qmi_wwan.c:129,313` in raw-ip mode) — all under `src/linux-6.12/drivers/net/…`. The WWAN core offers `IFLA_WWAN_LINK_ID` links (`include/uapi/linux/wwan.h:10`, per `SS333_LLI_BRINGUP.md` §7).
- [GEN][C] NetworkManager's MM backend maps `MM_BEARER_IP_METHOD_PPP → PPP`, `STATIC → STATIC`, `DHCP → AUTO`. It takes the data port from `mm_bearer_get_interface()`, applies the bearer MTU (`mm_bearer_ip_config_get_mtu` → `nm_l3_config_data_set_mtu`), and for IPv6 accepts a missing address under DHCP/"SLAAC". If the bearer gives a link-local address, NM derives the interface identifier from it (`nm_utils_ipv6_interface_identifier_get_from_addr`) — [nm-modem-broadband.c:252-264, 1092-1174, ~1180-1240](https://gitlab.freedesktop.org/NetworkManager/NetworkManager/-/blob/main/src/core/devices/wwan/nm-modem-broadband.c). NM latest tag 1.58.1 (2026-08-21) — [NM tags](https://gitlab.freedesktop.org/NetworkManager/NetworkManager/-/tags)
- [GEN][C] MM's own XMM7360-RPC bearer (a custom protocol whose data runs on a WWAN netdev) reports `MM_BEARER_IP_METHOD_STATIC` with address and DNS taken from the modem's RPC reply — [mm-bearer-xmm7360.c:141-143](https://gitlab.freedesktop.org/mobile-broadband/ModemManager/-/blob/main/src/plugins/intel/mm-bearer-xmm7360.c)
- [GEN][C] systemd **260** (2026-03-17): "systemd-networkd gained integration with ModemManager via the 'simple connect' protocol. A new [MobileNetwork] section … APN=, AllowedAuthenticationMechanisms=, User=, Password=, IPFamily=, AllowRoaming=, PIN=, OperatorId=, RouteMetric=, and UseGateway=" — [systemd NEWS](https://github.com/systemd/systemd/blob/main/NEWS). Arch ships systemd 262.1 — [archlinux.org](https://archlinux.org/packages/search/json/?name=systemd)
- [GEN][C] libsamsung-ipc GPRS messages: `DEFINE_PDP_CONTEXT 0x0D01` (`enable, cid, apn[124]`), `PS 0x0D03`, `PDP_CONTEXT 0x0D04` (activation, with auth), `IP_CONFIGURATION 0x0D09` (`cid, field_flag, ip[4], dns1[4], dns2[4], gateway[4], subnet_mask[4]`), `HSDPA_STATUS 0x0D0C`, `CALL_STATUS 0x0D10` (`cid, status`), `PORT_LIST 0x0D11` — [include/gprs.h](https://git.replicant.us/replicant/hardware_replicant_libsamsung-ipc/plain/include/gprs.h)

### Inferences
- [HW][L] PDP bring-up the daemon must do: (1) GPRS `DEFINE_PDP_CONTEXT` with cid + APN; (2) `PDP_CONTEXT` enable with auth; (3) wait for `IP_CONFIGURATION` / `CALL_STATUS`; (4) map cid → `rmnet(cid-1)` (needs confirmation, see Gaps), set the MTU, bring the link up; (5) publish a Bearer with `Interface=rmnetN`, `Ip4Config{method=STATIC, address, prefix (from subnet_mask), gateway, dns1/2, mtu}`, and for IPv6 `Ip6Config{method=DHCP, link-local address carrying the network-assigned IID}` so NM or networkd runs SLAAC; (6) on teardown, deactivate the context and report `Connected=false`.
- [HW][L] For the mainline port, switch rmnet to `ARPHRD_RAWIP` (or `ARPHRD_NONE`) with `IFF_NOARP | IFF_POINTOPOINT`; keep `ARPHRD_PPP` only if userspace will run IPv6 itself. Registering through the WWAN core (`wwan_register_ops`) would also give `ip link add … type wwan linkid N` and udev `wwan` visibility, which MM likes. That conflicts with keeping the legacy UAPI (`SS333_LLI_BRINGUP.md` §7 already notes this trade-off).
- [GEN][L] A raw-IP P2P netdev needs no gateway MAC. NM installs the default route on the device; a gateway in `Ip4Config` is optional.

### Gaps
- The cid ↔ rmnet index ↔ SIPC channel mapping, and how the CP tells the AP which rmnet carries a context (possibly `IPC_GPRS_PORT_LIST` 0x0D11): not verified.
- Whether SS333 delivers IPv6/IPv4v6 configuration through an extended `IP_CONFIGURATION` (libsamsung-ipc's struct is IPv4-only): unknown.
- The role of `multipdp` ioctls on the mainline port (flow control `PROTOCOL_SUSPEND/RESUME`): see `SS333_LLI_BRINGUP.md` §2.2; not researched here.

## 3. Desktop clients on Hyprland (no Phosh) and what they need from the backend

### Takeaway
All mainstream clients run outside Phosh and want the MM D-Bus API: GNOME Calls (MM provider; it also
has an oFono provider), Chatty (MM only), Spacebar (MM only), Plasma Dialer (MM by default, oFono
optional at build time) and mmsd-tng (MM only). On Hyprland the extra pieces are a notification daemon
(mako, swaync or dunst), feedbackd (ringtone and haptics through libfeedback), an NM secret agent for
the SIM PIN, and autostarting the Calls and Chatty daemon instances.

## 4. Voice-call audio: WM1814 in mainline, AIF2 routing, mainline precedents, UCM/callaudiod/WirePlumber, and what the CP needs

### Takeaway
The WM1814 is supported in mainline as a WM8998 variant (same chip ID 0x6349, driven by `wm8998.c`).
The project's own `gts28_wm1814.c` covers AIF1 only. On this board the CP masters the AIF2 PCM clocks:
codec slave, FLL2 locked to AIF2BCLK. That differs from mainline tm2_wm5110 (codec master, FLL2 from
MCLK1). The closest mainline pattern is the codec-to-codec "Voice call" link in `aries_wm8994.c`
(Samsung Galaxy S). On the CP side, Android sent only "audio path", "volume", "mute", "two-mic" and
"clock STOP" sound messages through libsecril-client; it never sent a clock START. Desktop switching is
now done by WirePlumber 0.5.11+, which reacts to MM Call objects by selecting a UCM profile named
"Voice Call…".

### Inferences
- [HW][L] Mainline design: extend `gts28_wm1814.c` with an aries-style codec-to-codec link. The machine registers an ext DAI "Modem" (or a `gtm601`-style dummy codec node) with `Modem RX/TX` widgets, linked to `wm8998-aif2`. Settings: `c2c_params` 8 kHz (plus a 16 kHz entry for WB-AMR), format I2S/DSP per CP, **codec as clock consumer** (CBC_CFC, the downstream "Slave"), `ignore_suspend`. On power-up: FLL2_REFCLK = MCLK1 24 MHz, FLL2 source = AIF2BCLK (256/512 kHz), ASYNCCLK 49.152 MHz, ASYNC rate 8 k/16 k. With c2c, DAPM powers AIF2 when the UCM routes complete, so no PCM has to be held open. A tm2-style PCM link (`ops->hw_params`, opened by a q6voiced-like helper) is the fallback.
- [HW][L] UCM: a "Voice Call" verb whose EnableSequence transcribes the `incall_nb-speaker`/`-speaker-mic` csets above, with devices Speaker / Headphones / Headset mic and no Earpiece (none exists). WirePlumber then switches automatically as soon as the IPC daemon publishes MM Call objects with correct `State`. callaudiod and GNOME Calls' libcallaudio remain only for speaker toggle and mute.
- [HW][S] Because Android never sends SOUND_CLOCK_START, the CP probably starts AIF2 BCLK/LRCLK by itself when the call connects (or on `AUDIO_PATH_CTRL`), and stops it on `CLOCK_CTRL sync=0` after the call. The daemon's minimal SND sequence: on call active, `AUDIO_PATH_CTRL` (speaker/headset) + `SPKR_VOLUME_CTRL`; on mute, `MIC_MUTE_CTRL`; on call end, `CLOCK_CTRL(0)`; listen for `WB_AMR_STATUS` to choose 8 k or 16 k. Since FLL2 locks to a CP-driven BCLK, codec power-up order matters (FLL2 cannot lock before the CP clocks run).
- [HW][S] The OEM→IPC mapping inside libsec-ril is proprietary. The "next-gen" OEM path values (speaker 0x07, headphone 0x08) may be passed to `IPC_SND_AUDIO_PATH_CTRL` unchanged, which would differ from libsamsung-ipc's older 0x06/0x07 values. Verify with IPC traces before relying on either.

### Gaps
- PCM format on AIF2 (I2S vs DSP-A, slot count, mono vs stereo; Android opened 2-ch S16 PCMs) and BCLK polarity: not derivable without the vegas AIF2 register dump or a scope.
- ASRC rate-2 default on WM1814 under mainline (no control exposed): must be read from the register map at runtime.
- Exact SS333 IPC SND payloads and when the CP emits `WB_AMR_STATUS`: no SS333 trace available.
- Whether CP accepts codec-master mode (`aif2mode=1`) on this board: Android used Slave only.

## 5. SIM (PIN, toolkit) and GNSS scope

### Takeaway
SIM access goes through the CP only (Samsung-IPC SEC/SAT groups). Clients expect MM's `Sim` object and
`Modem.UnlockRequired`, and NetworkManager asks for the PIN through a secret agent. MM has no SIM
Toolkit API (oFono does). GNSS is **not** part of the modem: the SM-T715 has a separate Broadcom BCM4752
on UART `/dev/ttySAC0` at 921600 baud, driven by Broadcom's proprietary `gpsd`/glgps, so it is out of the
modem scope.

- [HW][C→scope] GPS is a separate UART chip, not CP-integrated: it belongs to a GNSS work item (power GPIO + UART + a protocol stack), not to the Samsung-IPC daemon. MM `Location` can stay unimplemented, or carry only the 3GPP cell location (LAC/CI) from IPC NET messages.

## 6. Precedents of custom-protocol modems in ModemManager/oFono, and lessons

### Takeaway
The best precedents are: **XMM7360 RPC** (a custom binary protocol taken all the way into MM: kernel port
type in 2022, MM port detection in 2024, full plugin in May 2025, still not in a stable MM release);
**samsungipcd** and **libsamsung-ipc** (Samsung IPC → AT bridge; libsamsung-ipc covers an `ss333`-type
modem on herolte); the 2012 oFono **samsungipc** patchset, declared a dead end; and oFono's
**isimodem**, **rilmodem** and **qmimodem** as examples of non-AT oFono drivers. Lesson: the cost is
less in the protocol encoder than in discoverability (udev/port type), the data path (netdev vs PPP),
upstream review time, and power and suspend robustness.

### Cited Findings
- [GEN][C] Kernel: the iosm driver gained an RPC port type for XMM modems, renamed `WWAN_PORT_XMMRPC` during review (net-next, Oct 2022) — [LKML v2](https://lore.kernel.org/lkml/20221029090355.565200-1-shaneparslow808@gmail.com/T/). ### Inferences
- [GEN][L] Lesson 1 (discoverability): MM finds modems through udev subsystems and port types. A misc char device (`/dev/umts_ipc0`) is invisible to MM unless the kernel exposes a WWAN port (an UAPI addition, as XMMRPC needed) or MM's core is patched. That pushes the cheapest designs toward bypassing MM (implementing its D-Bus API) or emulating AT.
- [GEN][L] Lesson 2 (data path): AT emulation drags in PPP (samsungipcd). Native designs (XMM7360 plugin, ofono2mm) hand NM a real netdev with STATIC/DHCP IP config. SM-T715 already has raw-IP rmnet netdevs, so any design that does not use them wastes the kernel work.
- [GEN][L] Lesson 3 (timeline): even with a working out-of-tree implementation, XMM7360 RPC took ~11 months of MM review (Jun 2024 → May 2025) and is still not in a stable MM (1.24.x) as of 2026-10-29. For a single tablet, upstream MM inclusion should not be on the critical path.
- [GEN][L] Lesson 4 (robustness): XMM7360 reports freezes after suspend, and the downstream SS333 driver has PM/wakelock machinery (`SS333_LLI_BRINGUP.md` §3, §7). Suspend, CP crash and silent reset (IOCTL_MODEM_STATUS / POLLHUP) must be handled inside the daemon, with a modem re-export (MM object removed and re-added) visible to clients.
- [HW][L] Lesson 5 (protocol reuse): reusing libsamsung-ipc's message codecs (GPL-2.0+) is the shortest path to CALL/SMS/SEC/NET/SS/SND/GPRS coverage. herolte support shows these codecs were exercised on an `ss333`-type CP, but herolte's GPRS activation is a stub, so mobile data and IPv6 will need fresh reverse engineering (libsec-ril.so strings, IPC traces).

### Gaps
- MM maintainers' position on plugins for protocols with no kernel WWAN port type: not found.
- How many messages differ between XMM626-era Samsung IPC and SS333 (VoLTE/IMS, IPv6 PDP, new NET RAT values): unknown without traces.
- FSO/fsogsmd and other historic Samsung-IPC userspaces (SHR, 2011-2013) were not researched.
