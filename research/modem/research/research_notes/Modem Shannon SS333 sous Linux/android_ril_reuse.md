## Q1. Halium/libhybris: how oFono talks to a vendor rild, which plugin each Halium generation uses, and the minimum Android environment for an Android 7 rild (is binder needed?)

### Takeaway
With an Android 7 (pre-Treble) rild the whole interface is one Unix stream socket, `/dev/socket/rild`, that the host's oFono opens as uid 1001 ("radio"); Halium 5.1/7.1 ports used exactly this (Jolla's `ofono-ril-plugin`), while Halium 9+ ports talk to the HIDL/AIDL IRadio HAL over binder (`ofono-ril-binder-plugin` or `ofono-binder-plugin`). An Android 7 rild needs no binder IPC: `rild.c` has no binder call, and `libril` links `libbinder` only for the `Parcel` serialization class. What it does need is a bionic runtime, an init-style inherited socket, an Android property area, uid/capability setup, and the Samsung-specific files and device nodes (`/efs`, `/dev/umts_*`, multipdp sysfs).

### Inferences
- [likely] For the Android 7 socket rild with libsec-ril, binder IPC is not needed, provided libsec-ril.so itself does not call binder services (Samsung OEM services, `libsecnativefeature`). This has not been verified: the next step is `readelf -d libsec-ril.so` (DT_NEEDED) plus a strings check for `servicemanager`/`IServiceManager`, run on the owner's own copy.
- [likely] Minimum environment for an Android 7 rild + libsec-ril on our Arch system: (1) the bionic linker and libs at Android paths (`/system/bin/linker`, `/system/lib/{libc,libm,libdl,liblog,libcutils,libutils,libbinder,libhardware_legacy,librilutils,libril}.so` plus libsec-ril's own deps); (2) a launcher that creates `/dev/socket/rild` (and `rild-debug`), passes the fds as `ANDROID_SOCKET_rild=<fd>`, then runs rild as uid 1001 with the three capabilities; (3) a property area plus a `property_service` socket (the stock Android 7 init in an LXC container, Halium 7.1 style, or a small custom property daemon seeding a legacy single-file area); (4) `/efs` mounted read-write with the original contents; (5) `/data/misc/radio` and possibly the telephony provider database paths; (6) `/dev/umts_*` and multipdp sysfs owned by group radio; (7) `/sys/power/wake_lock` (`CONFIG_PM_WAKELOCKS`), or wakelock calls failing harmlessly; (8) SELinux off: rild does not need it.
- [likely] The host client must connect with uid 1001. Bionic's `getpwuid()` maps 1001 to "radio" whatever the host's `/etc/passwd` says, so creating a host user `radio` with uid 1001 (as Sailfish does with `Identity=radio:radio`) is the simplest fix.
- [speculative] The `telephony.db` / `preferred-apn.xml` symlinks suggest that Samsung's stack (cbd or libsec-ril) reads Android's APN database directly; without it, initial-attach APN selection may misbehave. Check with strace once rild runs.

### Gaps
- DT_NEEDED and the property list read by libsec-ril.so are unknown (not inspected, by constraint). These two facts decide how much of `/system` must be shipped.
- No public document describes running a Samsung libsec-ril without Android init; every precedent ran it under Android's own init (Halium or Android).

## Q2. Running Android vendor userspace on a mainline kernel: containers, "hybris on mainline", and the kernel features an armv7 bionic rild needs on 6.12

### Takeaway
I found no public precedent of a vendor rild plus vendor RIL running on a mainline kernel: Halium, Droidian and UBports all rely on the Android vendor kernel, and Waydroid (Android userspace on mainline with binderfs and memfd) does not do telephony. For our narrow case (Android 7, socket mode, armv7, 32-bit kernel), mainline 6.12 removes three Android-era interfaces that matter: the 32-bit binder protocol (gone in 4.18), `/dev/alarm` (gone in 4.0) and ashmem (gone in 5.18). Only `/dev/alarm` is known to be referenced by libsec-ril; binder and ashmem matter only if something in the chain actually uses them.

### Cited Findings
- {generic} [confirmed] Droidian: "We rely on the Android Linux kernel and drivers to make all of the functionality provided by Android drivers work"; devices ported to Ubuntu Touch "with Halium 9 or later" can likely run Droidian (Halium 7.1 not mentioned) — [Droidian FAQ](https://docs.droidian.org/faq)
- {generic} [likely] Halium's planning document notes that a device can run a mainline kernel only "if the device is mainlined" (search-result excerpt) — [Halium Planning](https://halium-docs.readthedocs.io/en/latest/project/Planning.html)
- {generic} [confirmed] Mainline 6.12 still has `ANDROID_BINDER_IPC` (depends on MMU), `ANDROID_BINDERFS`, and `ANDROID_BINDER_DEVICES` (default `"binder,hwbinder,vndbinder"`) — [drivers/android/Kconfig @ v6.12](https://github.com/torvalds/linux/blob/v6.12/drivers/android/Kconfig)
- {generic} [confirmed] The 32-bit binder protocol was removed by "ANDROID: binder: remove 32-bit binder interface" (Martijn Coenen, posted 2018-05-04, commit 1190b4e38f97); `ANDROID_BINDER_IPC_32BIT` is present in the v4.17 Kconfig and absent from v4.18 (checked on raw Kconfig files) — [lore patch](https://lore.kernel.org/lkml/20180504195728.72932-1-maco@android.com/), [Kconfig v4.17](https://github.com/torvalds/linux/blob/v4.17/drivers/android/Kconfig), [Kconfig v4.18](https://github.com/torvalds/linux/blob/v4.18/drivers/android/Kconfig)

### Inferences
- [likely] On 6.12 ARM32, the socket-mode Android 7 rild needs from the kernel only standard features: Unix sockets, capabilities, `/proc`, a wakelock interface, the ported `modem_v1` nodes and rmnet netdevs, and `CONFIG_TUN` if libsec-ril really opens `/dev/tun`. No binder, binderfs or ashmem should be needed, so this route is simpler than Waydroid or Halium 9+.
- [likely] If anything in the chain did need binder with the stock Samsung Android 7 `libbinder` (most likely built with the 32-bit protocol, as a 32-bit-kernel Nougat device), it would fail on any kernel ≥4.18. A rebuilt Android 7 userspace with `TARGET_USES_64_BIT_BINDER := true` would avoid this.
- [speculative] `/dev/alarm` is missing on 6.12; Samsung code typically uses it for RTC-wakeup timers. Expect a logged error and either a fallback or degraded timing (missed modem watchdog or keep-alive). A small shim (an LD_PRELOAD in bionic, or a char device emulating the old `ANDROID_ALARM_*` ioctls) is a fallback if it turns out to matter.
- [speculative] Container choice: the "mini-Halium" option (LXC running a stripped Android 7 init that only starts rild and the property service) reuses Android's own init semantics (sockets, properties, uid and caps) at the cost of ~100 MB of `/system`. A bare chroot plus a custom launcher is lighter, but the properties have to be reimplemented. The LOADER_SPEC verdict that a bionic shim set for `cbd` is "a multi-week project" (`research/modem/LOADER_SPEC.md:10-23`) applies only partly: rild is dynamically linked, so the stock bionic libs supply the property and logging code, and only the services behind them (property service, logd or `/dev/log`) must exist.
- [speculative] Loading the bionic libsec-ril.so into a glibc rild through libhybris (instead of running a bionic rild) is possible in principle, but I found no precedent for RIL; it adds libhybris's Android 7 linker emulation for no clear gain.

### Gaps
- No example of rild + vendor RIL on a mainline or non-Android kernel was found (searches of Halium, postmarketOS, Droidian and Waydroid material).
- Whether Waydroid supports armv7/ARM32 hosts was not checked; it matters only for the Android 8+ route.

## Q3. Precedents: Linux ports on Samsung Exynos devices with Shannon (and related) modems, and the workarounds they needed

### Takeaway
The only Shannon device with documented working telephony on a hybris distribution is the Galaxy S7 Exynos (Exynos 8890 + Shannon 335). Its Halium 11 Ubuntu Touch port (2022) reports calls, SMS, mobile data and call audio working, through the HIDL IRadio of LineageOS 18.1's open-source libril, not through socket-mode stock libril. Samsung ports converge on the same oFono knobs: `emptyPinQuery=false`, `radioPowerCycle=false`, `confirmRadioPowerOn=false`, `SetRadioCapability=off`, `enableCellBroadcast=false`. I found no Linux telephony port for the Tab S2 LTE (T715/T815), the Galaxy S6 or the Note 5. The Exynos 5433 Note 4 (N910C) uses an Ericsson M7450 modem, not Shannon; its 2020 Sailfish attempt had rild segfaulting as soon as oFono initialised.

## Q5. The Android 7 RIL socket protocol, and whether upstream oFono `rilmodem` still supports it in 2025-2026

### Takeaway
The Android 7 RIL socket protocol is a 4-byte big-endian length followed by an Android Parcel. Requests are `{int32 request, int32 serial, args}`. Responses start with `int32 type`: 0 = solicited `{serial, error, data}`, 1 = unsolicited `{id, data}`, and 2/3/4 are ACK variants used only when the vendor RIL reports version ≥13. Upstream oFono still ships `rilmodem` in 2.19 and in 2026 HEAD, but it has had no functional change since December 2021, only covers AOSP/MTK/Infineon/QCOM-MSIM/IMC vendors, treats any non-zero type as unsolicited, exits on parcels over 8 KB, and parses data calls in the v6 layout. It is usable but unmaintained for this purpose. Jolla's plugin is more robust but tied to the Sailfish oFono fork (1.29).

- [likely] Upstream `rilmodem` with RIL v12: the data-call list will carry v11 entries (extra `pcscf` string and `mtu` int). The v6 parser is fine for the first entry but misreads later ones when several contexts are listed (default plus IMS or MMS), and an oversized parcel (cell-info lists, Samsung OEM unsolicited) would kill `ofonod`. Jolla's plugin handles these, but it targets the Sailfish fork, which has no Arch package (it must be built from source with libgrilio and libglibutil).
- [likely] For a Hyprland/Omarchy desktop the realistic stack is rild → oFono (Sailfish fork + ofono-ril-plugin + Samsung quirks) → oFono2MM → ModemManager clients (`mmcli`, NetworkManager, GNOME Calls, Chatty). The alternative is upstream oFono 2.x `rilmodem` plus a new Samsung vendor quirk set, with the same oFono2MM bridge.

### Gaps
- No public report of upstream oFono 2.x `rilmodem` being used against any vendor RIL after 2021 was found; that it still works in practice is unverified.

## Q6. Blob provenance and redistribution

### Takeaway
LineageOS never ships `libsec-ril.so` or `cbd` in source form; they are extracted from a device or stock image by `extract-files.sh` following `proprietary-files.txt`. The project's copy comes from the owner's own tablet and must stay private, together with `/efs`, which holds per-device identity and NV data.

### Cited Findings
- {T715} [confirmed] LineageOS lists `bin/cbd` and `lib/libsec-ril.so` as proprietary files to extract (cm-14.1) — [proprietary-files.txt](https://github.com/LineageOS/android_device_samsung_gts28ltexx/blob/cm-14.1/proprietary-files.txt); the extraction script writes into `vendor/samsung/<device>/proprietary` — `src/device_gts2-common/extract-files.sh:3-6`
- {T715} [confirmed] The project has already retrieved `libsec-ril.so` from the tablet's own backup — `PROGRESS.md:55`
- {T715} [confirmed] rild reads `/efs` (IMEI, `mps_code.dat`, FactoryApp) — `src/device_gts28ltexx/sepolicy-ril/rild.te:9-17, 53-62`

### Inferences
- [likely] Redistribution constraint: Samsung's blobs are proprietary and unlicensed for redistribution. Any published recipe should extract them from the user's own device or firmware (as LineageOS does), never bundle them. `/efs` contents must never leave the device or be shared.

### Gaps
- None material to the engineering decision.

## Q7. Effort and risk: the hybris/container route versus a native RIL

### Takeaway
Reusing the vendor RIL is the fastest way to reach network registration, SMS and probably data. The cheapest form is Android 7 socket mode: a bionic chroot or mini-LXC with rild + libsec-ril, then oFono with a Samsung quirk set, then oFono2MM. It leaves the project dependent on a crash-prone closed 32-bit blob, on an unmaintained Android 7 bionic, and on oFono forks, and it does not remove the hard part, call audio. A Halium-9+-style HIDL route has better client maintenance (ofono-binder-plugin, active in 2026) and the only Shannon precedent with working calls, but it needs a full Android 10/11 userspace in a container. A native daemon (libsamsung-ipc-style, see `samsung_ipc_free_rils.md`) is months of reverse engineering, but it ends in maintainable code. The vendor-RIL route doubles as the protocol oracle for that effort.

### Cited Findings
- {T715} [confirmed] The project's dossier already assumes "rild replacement can reuse libsec-ril.so initially — only `cbd` must be reimplemented" — `research/modem/SS333_LLI_BRINGUP.md:679-680`; and judges a bionic shim for the static `cbd` "a multi-week project on its own" versus ~500 lines for a independent loader — `research/modem/LOADER_SPEC.md:10-23`
- {Shannon-other: S7} [confirmed] Working calls, SMS, data and audio routing came from a Halium 11 + LineageOS 18.1 HIDL stack — [UBports forum 8025](https://forums.ubports.com/topic/8025/samsung-galaxy-s7-s7-edge-exynos-herolte-hero2lte-call-for-testing), [Kethen repo](https://github.com/Kethen/samsung-exynos8890-ubuntu-touch)
- {Samsung-other: S2 XMM6260} [confirmed] In socket mode, signal bars and a first call came the same evening, once one oFono knob was changed — [#sailfishos-porters 2020-01-30](https://irclogs.sailfishos.org/logs/%23sailfishos-porters/2020/%23sailfishos-porters.2020-01-30.log.html)
- {5433-nonShannon: N910C} [confirmed] In socket mode, rild crashed whenever oFono started and no fix was recorded — [#sailfishos-porters 2020-06-22](https://irclogs.sailfishos.org/logs/%23sailfishos-porters/2020/%23sailfishos-porters.2020-06-22.log.html)
- {generic} [confirmed] Upstream oFono `rilmodem` has been functionally idle since 2021-12 (Q5); `ofono-ril-plugin` was last released 2024-03, while `ofono-binder-plugin` was released 2026-09 — [ofono-ril-plugin](https://github.com/mer-hybris/ofono-ril-plugin), [ofono-binder-plugin](https://github.com/mer-hybris/ofono-binder-plugin)
- {Shannon-other: S7} [conflicting] The S7 Halium 11 tested-status post does not mention VoLTE at all ([UBports forum 8025](https://forums.ubports.com/topic/8025/samsung-galaxy-s7-s7-edge-exynos-herolte-hero2lte-call-for-testing)), whereas a search excerpt of the S7 focal device page lists "VoLTE calling" among its feature rows, with no status visible ([devices.ubuntu-touch.io/device/herolte/release/focal](https://devices.ubuntu-touch.io/device/herolte/release/focal)). ### Inferences
Effort estimates are [speculative]. They count only userspace work once the kernel `modem_v1`/LLI port and the independent loader already put the CP online (prerequisites shared by all routes).

- [likely] Quick wins in any vendor-RIL route: radio power, SIM status and PIN, network registration and operator name, signal, SMS send/receive (precedents reach these first). USSD and supplementary services usually follow cheaply.
- [likely] Medium: mobile data. libsec-ril brings rmnetN up through multipdp, then the host must configure IP, DNS and routes, and NetworkManager or ModemManager must be told (oFono2MM, or an oFono hook). The upstream v6-only data-call parser and Samsung's `net.temp.mtu` / interface-config properties add friction.
- [likely] Hard: call audio. It needs CP-side routing and clock commands over "Multiclient" OEM_HOOK_RAW, codec AIF2 configuration on the mainline WM1814 driver, and rate tracking via unsolicited 20017/20022. No precedent covers it outside Samsung's own audio HAL.
- [speculative] Not feasible: IMS/VoLTE. Samsung's IMS stack runs in the Android framework and apps rather than in libsec-ril, and no Exynos hybris port documents tested VoLTE (see the conflicting S7 sources above). SIM toolkit UI and phonebook via OEM requests are probably out of reach too.
- [speculative] Recommended sequencing: (1) once the independent loader brings the CP online, try A1 in a throwaway chroot to learn the blob's real dependencies (DT_NEEDED, properties, files) and capture SIPC5 FMT traffic on `umts_ipc0` while doing SIM, registration, SMS, data and call operations. (2) Keep A1 as the interim daily driver if it is stable. (3) Use the captured traffic as the specification for route C, which removes bionic, the blob and the oFono forks in the long run. Route B is worth considering only if A1 hits a binder or Samsung-libril dependency it cannot work around.

### Gaps
- Real libsec-ril stability under a non-Android client on this exact firmware (T715XXU2CQCL-era N blobs) is unknown until tested; no T715 precedent exists.
- Whether the T715's stock libsec-ril handles RFS and NV itself or expects `cbd` to (the dossier shows the RFS verb set in libsec-ril strings) changes how cleanly route A coexists with the independent loader; to be settled by the first run.
